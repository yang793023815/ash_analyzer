问题发生时 DBA 往往不在场。ash_analyzer 用 ASH 持久化数据做事后复盘：定位问题精确窗口 → 分类症状 → 找到根阻塞者（以及它自己在等什么）→ 还原完整等待链（含 RAC 跨实例）→ 判定会话是否卡死。

覆盖数据源

gv$active_session_history（实时全库 1s）· v$（本实例 1s）· dba_hist_active_sess_history（AWR 10s）· 任意 CTAS/impdp 导入的 ASH 表——按列自动识别布局，缺列自动降级

可移植性

单文件、纯 bash + sqlplus。拷到任意 Oracle 服务器即可运行：自动探测 ORACLE_SID（pmon，跳过 +ASM/-MGMTDB）与 ORACLE_HOME（oratab），支持 -s 多实例切换、-c 远程连接串

01部署与运行

chmod +x ash_analyzer
./ash_analyzer help                 # 中文帮助
./ash_analyzer info                 # 体检默认数据源 (hist)
./ash_analyzer info -i gv           # 体检实时 gv$ 视图
./ash_analyzer info -s lcbdg1       # 多实例主机切换目标库
./ash_analyzer events -c 'user/pwd@tns' -m 60

无需任何配置文件；-s SID 在多实例主机（如 qone1 上的 orcl1 / lcbdg1）间切换，-c 支持远程 EZConnect / TNS。

02数据源与自动识别

-i 参数实际数据源布局间隔

识别按列存在性：有 INST_ID → gv；有 SNAP_ID+INSTANCE_NUMBER → hist；仅 INSTANCE_NUMBER → hist 并提示；都没有 → single。19c/11.2 列集差异安全：缺 BLOCKING_INST_ID 时阻塞链退化为仅同实例匹配（有提示）、缺 PGA/TEMP 列时 res 干净退出、缺 SQL_EXEC_ID 跳过长执行识别。

跨环境导入分析（v1.1）其他库导出的 ASH 表（含视图）用 -i 直接分析，布局自动识别；数据 DBID 与本地不一致时 info 自动提示。源库的 current_obj#/user_id/SQL 文本属源库，配套映射表解析：
-objmap 对象表（OBJECT_ID/OWNER/OBJECT_NAME）· -sqlmap SQL文本表（SQL_ID+SQL_TEXT|SQL_FULLTEXT）· -usermap 用户表（USER_ID/USERNAME）。多库合并导入用 -D dbid 锁定。

04核心方法论：六步下钻

定位窗口

./ash_analyzer trend -t '2026-09-20 16:40:00' -T '2026-09-20 17:00:00'

活动会话突增段 = 问题起点（每分钟直方 + 峰值样本）。

症状分类

./ash_analyzer events -t '2026-09-20 16:44:00' -T '2026-09-20 16:50:00'

顶级等待事件定性：CPU 饱和 / IO / 锁 / 集群。

找根

./ash_analyzer blockers -t '2026-09-20 16:44:00' -T '2026-09-20 16:50:00'

Root Blocker = 等待树终点；看它的 ROOT_EVT（它自己在等什么），那才是病灶。

验证链路

./ash_analyzer chain -S 65 -t '2026-09-20 16:45:00' -T '2026-09-20 16:46:00'

从受害者到终点的完整 path，跨实例边按容差自动接上。

卡死判定

./ash_analyzer detail -S 406 -t '2026-09-20 16:44:00' -T '2026-09-20 16:46:00'

seq# 不变 = 卡死在同一等待；seq# 递进 = 在走只是慢。

补充维度

./ash_analyzer obj ...  /  res ...  /  text -q 9zg9qd9bm4spu

热点对象、PGA/临时段、SQL 文本。

05阻塞链实现原理

向上遍历：connect by prior blocking_session = session_id——子行是父行的持有者，从受害者走到链终点（connect_by_isleaf=1），根阻塞者即等待树终点。

同实例边：prior sample_id = sample_id 精确匹配。跨实例边：RAC 两实例采样网格存在相位差——96 环境实测 inst1/inst2 的 sample_id 序列完全独立、同秒采样零重叠，跨实例持有者在 ±2s 内命中 0、±5s 命中 154/155（99.4%）。因此跨实例改用时间容差：

( prior instance_number <> instance_number
  and abs((cast(prior sample_time as date) - cast(sample_time as date))*86400) <= 5 )   -- hist 默认 5s / gv 2s / -w 可调

配套防护：prior blocking_inst_id = instance_number（持有者实例对位）、serial# 匹配防 SID 重用、DBID 匹配防多库导入串库。

实测校准（96 / 2026-09-20 事故窗口）155 条跨实例阻塞行：±2s 命中 0，±5s 命中 154（99.4%）；10 天 hist 全表阻塞树分析 0.5 秒完成。

06真实案例：2026-09-20 16:43–16:50 归档断档事故

tool 输出还原的完整等待链：2.4 → 1.19 → 1.65 → 1.406 → 1.317（跨实例边为容差匹配）

结论与当时现场一致：归档目的地写入慢导致 log file switch (archiving needed)，传导到 LGWR 控制文件竞争、再到业务等待。root_evt 列直接指向病灶层级。

07判读要点

  • est_sec = 样本数 × 采样间隔（hist 10s / gv 1s），近似 DB time 秒。
  • ON CPU 数接近物理 CPU 数 → 结合 OS 侧（run queue / OSWatcher）看，别只盯数据库。
  • root_evt 是真正病灶：等待者表面事件（如 library cache lock）常只是传导症状。
  • seq# 不变 = 卡死同一等待（hang）；seq# 递进 = 在走只是慢 / 循环等待。
  • iscycle=1 = 等待环（死锁类），重点排查。
  • STATUS=VALID 但持有者不在样本中 = 持有者空闲未被采样——ASH 机制固有限制，对照“直接阻塞者”表。
  • -g 实例过滤会切断跨实例等待链，RAC 全局分析慎用。
  • 导入表分析时 current_obj# / user_id 属于源库，需一并导入源库 dba_objects / dba_users 才能解析。
